Stateless app tierHybrid here is a deployment choice

  • A global load balancer splits traffic across clouds
  • The same container image runs in both — active-active
  • Scale out = add a replica. Any replica serves any request
  • Failure = drain a region, traffic reroutes in seconds
  • Cost of the second cloud is roughly linear
  • It works because the state lives somewhere else

Stateful data & AI tierHybrid here is an architecture decision

  • Data has gravity — terabytes do not move per request
  • Egress is charged per GB, on every read that crosses
  • Replication introduces consistency lag you must design around
  • Transactions, table locks and commits do not span clouds
  • The catalog is itself state — grants, policies, lineage
  • Scale out = pay twice and reconcile, not add a replica
You cannot put a load balancer in front of a lakehouse. Hybrid data architecture is not about running the same thing in two places — it is about choosing where the boundary cuts, and then being honest about what crosses it. The seven patterns that follow are the choices that are actually in use, ordered from least data crossing the boundary to most.

Federate
→ Pattern 1 · Read in place

The working set is stable and the reads are occasional, so caching pays and the transfer stays small. Lowest effort, and you keep one copy. This is what read-in-place is for.

Push compute to the data
→ Pattern 3, if a region pairing exists

The read recurs but the bytes cannot move. Run the engine next to the data and return only results. If there is no region pairing, fall back to federating plus a materialised curated slice — you then pay the transfer once per refresh instead of once per query.

Data is free
to move
Bring your own engine
→ Pattern 2 · Open catalog

Centralise storage and catalog in open format, keep engine choice open. Exploratory work runs on whatever engine the team already knows, against one governed copy.

Co-locate
→ Pattern 4 · Plane separation

The read recurs every run and the working set keeps shifting, so caching stops paying. Move the data once, continuously, and stop paying per query. A split execution plane here defers the migration rather than avoiding it.

Two patterns sit outside the grid. Domain separation (5) applies at any position — it is an organisational boundary, not a workload one, so it composes with all four quadrants. Edge and on-prem (6) is decided by physics and regulation, not preference.
Then answer the serving question separately. Pattern 7 is the only one where latency, not volume, is the binding constraint. A workload can federate its analytics and still need its serving tier colocated with the caller.
Federating data access and splitting the execution plane are two different decisions. Answer them separately, and answer them per workload rather than per platform. Most estates end up with two or three of these patterns running side by side, which is fine — what causes trouble is picking one globally and forcing every workload through it.
