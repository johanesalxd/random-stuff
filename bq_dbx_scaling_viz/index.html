Scenario Walkthrough: The "1 to 11" Query Problem

Which model is this? The fixed "one cluster per 10 concurrent queries" rule shown below is the documented behavior of classic & pro SQL warehouses. Serverless warehouses instead use Intelligent Workload Management (IWM): a new query is admitted immediately if capacity exists, otherwise it is queued, and the autoscaler adds clusters when queue wait time rises — there is no hard "query #11 → new cluster" trigger. The 10-query step model is kept here because it is concrete and easy to visualize; treat the exact threshold as illustrative.

Step 1: Single Query Run

Performance: Maximum (full cluster capacity)

Behavior: The query has exclusive access to the cluster's resources. With the selected cluster size, it runs on the full set of workers/cores in that cluster.

Step 2: Jobs 2-10 Added

Performance: Degrades as concurrency rises (Stuffing Effect)

Behavior: Additional queries are admitted onto the existing active cluster up to its concurrency limit. They now share the same CPU/memory, so each effectively gets a fraction of the cluster's throughput. (The even "DBU ÷ N" split shown is a simplification — real sharing depends on each query's resource profile, not a fixed per-query DBU quantum.)

Step 3: 11th Job Added

Performance: Split Experience

Behavior: The cluster is full (classic/pro) or the queue wait time crosses IWM's threshold (serverless), so a second cluster is provisioned.

  • The 11th Query: Routed to Cluster #2 and gets full speed (full cluster capacity).
  • The First 10 Queries: REMAIN on Cluster #1, continuing to run with shared resources. Running queries are not moved or rebalanced onto the new cluster.

Key Insight: Locked-In vs. Dynamic Rebalancing

In the SQL warehouse model, a query runs to completion on the cluster it was admitted to; when the autoscaler adds clusters, those new clusters take on queued/new queries rather than rebalancing in-flight ones.[1] Practical consequences can include:

  • Higher cost when several clusters run concurrently
  • Uneven experience — queries admitted during a busy period may run slower than later ones
  • Newly added clusters don't speed up queries already in progress

BigQuery differs here: fair scheduling reassigns slots to in-flight queries as capacity changes, within the reservation's / project's limits.[4]

Comparison: "Chunky" vs. "Seamless" Scaling

Aspect Databricks SQL Warehouse Google BigQuery
Scaling Unit Clusters (chunky) — the autoscaler adds or removes whole clusters of the chosen fixed size (e.g., Small, Large, X-Large).[1] Slots (granular) — reservations autoscale slot capacity up/down, rounded up to the nearest 50-slot increment; on-demand draws from a shared pool.[4]
Running Queries Locked-in — a query runs to completion on its assigned cluster; newly added clusters serve queued/new queries rather than in-flight ones.[1] Dynamic / rebalanced — BigQuery uses fair scheduling within a reservation, so slots are reassigned on the fly to running queries as capacity frees up or is added ("eventual fairness").[4]
The "Stuffing" Effect Can be pronounced — concurrent queries share a fixed cluster until the next cluster boots, so per-query throughput tends to drop as concurrency rises.[1] Usually milder — fair scheduling spreads work across a shared slot pool, so per-query impact is smoothed rather than bounded by one cluster's size.[4]
Cost / Billing Shape Multiple clusters may run at once, and early (locked-in) queries can't use a newly added cluster's resources.[1] Single pool scales dynamically, but autoscaled slots are billed per second with a 1-minute minimum and round up to 50-slot increments, so you can pay for more slots than a short query uses.[5][6]
Performance Predictability Variable — depends on when a query arrives (before or after cluster scaling).[1] Can be more consistent — fair scheduling evens out distribution, but the autoscaler is reactive and bounded by reservation limits (or ~2,000 slots/project, 20,000/org, on-demand).[4]

Technical Notes

  • IWM (Intelligent Workload Management): Databricks' ML-powered system for serverless warehouses. It predicts a query's resource needs, admits it immediately if capacity exists (otherwise queues it), and autoscales clusters when queue wait times rise.[1]
  • Classic/Pro concurrency rule: Classic and pro warehouses have a fixed limit of one cluster per 10 concurrent queries — this is the concrete rule the step model above mirrors.[1]
  • Fair Scheduling: BigQuery allocates slots within a reservation first equally across projects, then equally across each project's running jobs, reassigning them on the fly as queries start/finish ("eventual fairness").[4]
  • DBU (Databricks Unit): A billing metric, not a fixed resource allocation. Actual compute depends on cluster size (workers/cores).[2]
  • Slots: Virtual CPUs in BigQuery that can be dynamically allocated and reallocated during query execution; autoscaling rounds up to the nearest 50-slot increment.[4]
  • Fluid Scaling (opt-in): A reservation option that adjusts slots second-to-second and removes autoscaling's one-minute minimum, giving true per-second billing. It still scales in 50-slot increments and may grant a reservation slightly more or fewer idle slots than its exact fair share during rapid demand swings. Enabled per reservation at the admin-project level.[4][5]

Caveats & Limitations

Databricks — About This Visualization:

  • Illustrative threshold: The fixed 10-queries-per-cluster rule is exact for classic/pro warehouses; serverless with IWM scales earlier or later based on query complexity and queue wait time, so treat the number as illustrative.[1]

BigQuery — "Seamless" isn't unbounded or instant:

  • Discrete scaling steps: Autoscaling doesn't add capacity slot-by-slot — it scales up rounded to the nearest 50-slot increment, and the autoscaler is reactive and conservative by design.[4]
  • 60-second minimum: Autoscaled slots are billed per second with a one-minute minimum, and scaled capacity is retained for at least 60 seconds (the scale-down window) — unless Fluid Scaling is enabled (see Technical Notes).[5][6]
  • Capacity limits: Fair scheduling redistributes within available capacity, but that capacity is bounded — by a reservation's baseline + autoscale_max_slots, or by the on-demand ceiling of ~2,000 slots per project (20,000 per organization; BigQuery may occasionally exceed this to speed a query). Under contention, queries still wait for slots.[4][7]

Cluster Startup Times:

  • Serverless SQL Warehouses: Databricks maintains pre-warmed compute in its managed compute plane, so serverless warehouses typically start within seconds.[3] During peak demand or for less common sizes, the pool may need to provision new VMs, which takes longer.
  • Classic/Pro SQL Warehouses: These provision VMs from the cloud provider on demand, so cold starts are on the order of minutes (a common rule-of-thumb is ~2–5 minutes), depending on size and CSP capacity. Larger clusters take longer.
  • Pre-Warming Architecture: Serverless uses a shared pool of pre-booted VMs; a VM is assigned exclusively to your workload, then sanitized and returned to the pool after use. Pool capacity is finite and shared across customers in a region.[3]

Cloud Provider Dependencies:

  • CSP Capacity: Scaling is subject to cloud provider compute availability. During high-demand periods, VM provisioning can be delayed.
  • Not truly instantaneous: Serverless startup depends on pre-warmed pool availability; if the pool is exhausted, new capacity must be provisioned and startup slows accordingly.[3]
  • Regional Variations: Availability and performance vary by cloud region.
